## Project Overview

A TanStack Start app running on Netlify that uses **Netlify Database** (Postgres) for data and **TanStack AI Code Mode** for the LLM tool layer. The app is a "Database Reports" agent — users ask the AI to generate interactive reports (charts, tables, metrics) from a dataset of customers, products, and purchases.

## Requirements

- **Node.js 24** (pinned in `.nvmrc`) — `isolated-vm` only has prebuilt binaries for Node 24's ABI
- **pnpm** as package manager
- At least one AI provider API key in `.env.local` (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, or `GEMINI_API_KEY`)

## Commands

```bash
pnpm install              # install deps (also compiles isolated-vm native addon)
pnpm dev                  # start Vite dev server on :3000 (boots local Postgres in-process)
pnpm build                # production build (dist/client + server bundle)
pnpm test                 # vitest run

# Database (requires pnpm dev running in another terminal)
pnpm db:apply             # apply schema migrations from netlify/database/migrations/
pnpm db:seed              # seed demo data (35 customers, 20 products, 550 purchases)
pnpm db:reset             # drop everything, start over (then db:apply + db:seed)
pnpm db:generate          # regenerate migration from db/schema.ts via drizzle-kit
pnpm db:studio            # open Drizzle Studio GUI against local DB
pnpm db:seed:migration    # emit seed data as an idempotent SQL migration file
```

Full reset cycle: `pnpm db:reset; pnpm db:apply; pnpm db:seed`

## Architecture

### Framework Stack

- **TanStack Start** (React SSR framework) with file-based routing (`src/routes/`)
- **TanStack React Router** — route tree auto-generated in `src/routeTree.gen.ts`
- **Vite** with RSC plugin, Tailwind CSS v4, Netlify Vite plugin
- **Drizzle ORM** for database schema and migrations
- Server-side code runs as Netlify Functions via `@netlify/vite-plugin-tanstack-start`

### Path Aliases

- `#/*` and `@/*` both resolve to `./src/*` (configured in `tsconfig.json` and `vite.config.ts`)

### Two Feature Areas

The app has evolved through two stages — the original **Database Demo** and the current **Reporting Agent**:

1. **Reporting Agent** (current, `src/routes/index.tsx`): Full-page chat UI where users request reports. The AI generates interactive reports with charts, tables, and metrics rendered in a split panel.

2. **Database Demo** (legacy, documented in `CODE-MODE.md`): The original code-mode demo with direct tool calls. Components in `src/components/db-demo/` are still imported by the reporting page for code block rendering and VM event display.

### Key Data Flow

```
User prompt → POST /api/reports → LLM adapter (anthropic/openai/gemini/deepseek)
  → chat() with tools: [codeMode tool, new_report, list_reports, delete_report]
    → LLM calls new_report → creates ReportState server-side
    → LLM calls execute_typescript → code runs in sandboxed VM
      → sandboxed code calls external_queryTable / external_getSchemaInfo (DB tools)
      → sandboxed code calls external_report_* (report bindings to add components)
        → each binding emits SSE event → client receives via useChat onCustomEvent
```

### Code Mode / Sandbox

The LLM writes TypeScript that runs in a sandboxed VM instead of making individual tool calls. Configured in `src/routes/_reporting/api.reports.ts`:
- **Driver**: `isolated-vm` (Node.js native) with QuickJS fallback (`src/lib/create-isolate-driver.ts`)
- **Tools available in sandbox**: `external_queryTable`, `external_getSchemaInfo` (from `src/lib/tools/database-tools.ts`)
- **Report bindings**: ~25 `external_report_*` functions (from `src/lib/reports/create-report-bindings.ts`) that add/update/remove UI components

### Report System

Reports are real-time, component-based UI trees managed with a node graph:

- **Types**: `src/lib/reports/types.ts` — `UINode` tree with 18 component types (vbox, hbox, grid, card, chart, dataTable, metric, etc.)
- **Event protocol**: `UIEvent` with ops: `add`, `update`, `remove`, `reorder` — applied both server-side and client-side
- **Server state**: `src/lib/reports/report-storage.ts` — in-memory `Map<string, ServerReportState>` with signal registry, SSE controllers, and watcher subscriptions
- **Client state**: `src/components/reports/useReportState.ts` + `usePersistedReports.ts` — client-side node graph + localStorage persistence
- **Rendering**: `src/components/reports/ReportRenderer.tsx` → `NodeRenderer.tsx` renders the component tree; primitives in `src/components/reports/primitives/`

### Database Layer

- **Schema**: `db/schema.ts` — Drizzle definitions for `customers`, `products`, `purchases` (plus unused `posts`)
- **Migrations**: `netlify/database/migrations/` — auto-generated by `drizzle-kit generate`
- **Seed data**: `db/seed-data.ts` → loaded by `db/seed.ts` via raw `pg` driver
- **Connection**: `drizzle.config.ts` reads `NETLIFY_DB_URL` or `.netlify/state.json#dbConnectionString`
- **Query tools**: `src/lib/tools/database-tools.ts` — parameterized SQL via `getDatabase().pool.query()`, with column validation against `database-constants.ts`

### Server-External Packages

`vite.config.ts` marks these as external for SSR/RSC because they depend on on-disk layout or native binaries: `esbuild`, `pg`, `isolated-vm`, `quickjs-emscripten`, `quickjs-emscripten-core`, `@jitl/quickjs-wasmfile-*`. They are listed as direct dependencies so pnpm hoists them and Netlify's function packager includes them.

### API Routes

| File | Route | Purpose |
|------|-------|---------|
| `src/routes/_reporting/api.reports.ts` | `POST /api/reports` | Main chat endpoint — SSE stream with LLM, code mode, report tools |
| `src/routes/_reporting/api.report-sse.ts` | `GET /api/report-sse?reportId=` | SSE stream for real-time report updates |
| `src/routes/_reporting/api.report-event.ts` | `POST /api/report-event` | Handler execution (button clicks, etc.) |
| `src/routes/_reporting/api.invalidate.ts` | `POST /api/invalidate` | Signal invalidation → re-evaluate watchers and refresh subscribed components |

### LLM Providers

Configured in `src/routes/_reporting/api.reports.ts` — `getAdapter()` supports: `anthropic` (Haiku 4.5/4), `openai` (GPT-4o), `gemini` (2.5 Flash), `deepseek` (via OpenAI-compatible API). AI Gateway on Netlify auto-injects provider keys in production.

## Gotchas

- `pnpm dev` sets `EXPERIMENTAL_NETLIFY_DB_ENABLED=1` — without it the DB feature is skipped and `getDatabase()` throws
- The DB must be migrated (`pnpm db:apply`) and seeded (`pnpm db:seed`) before first use, or the app crashes on missing tables
- Report state is server-side in-memory — lost on server restart. Client-side reports persist to localStorage
- `db/seed.ts` starts with `TRUNCATE TABLE ... RESTART IDENTITY CASCADE` — never run against production data
- The code mode cache (`codeModeCache` in `api.reports.ts`) means driver + bindings are created once and reused across requests
